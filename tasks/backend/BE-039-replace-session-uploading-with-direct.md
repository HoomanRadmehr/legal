# BE-039: Replace session-based uploads with direct MinIO presigned uploads

Status: DONE
Priority: P0
Area: Backend
Related specs: BE-002, BE-007, BE-008, BE-009, BE-010, BE-013
Depends on: BE-018, BE-019, BE-022

## Goal

Replace the current session-based document upload implementation with a simple direct-to-MinIO upload flow.

The backend must:

1. Check whether the authenticated User may upload a document to the selected legal matter.
2. Create a pending Document record.
3. Return a short-lived presigned MinIO upload URL.
4. Never receive or proxy file bytes.
5. Verify the uploaded object after the frontend calls the complete action.
6. Publish backend-controlled status changes through the existing realtime infrastructure.

Do not introduce a separate UploadSession model.

The Document record itself represents the pending upload intent.

## Architecture

```text
POST /api/v1/documents/presign/
    ↓
Permission, metadata, quota and rate-limit checks
    ↓
Create Document(status=pending_upload)
    ↓
Return presigned MinIO URL
    ↓
Frontend uploads directly to MinIO
    ↓
POST /api/v1/documents/{document_id}/complete/
    ↓
Backend performs MinIO HEAD/stat verification
    ↓
Document(status=available)
```

The backend must never receive the uploaded file body.

## Business rules

1. MinIO buckets remain private.
2. The frontend must never receive MinIO credentials.
3. The frontend must never choose the final MinIO object key.
4. The object key is generated by the backend.
5. The object key is stored on the Document record.
6. Permission is checked during presign creation.
7. Permission is checked again during completion.
8. Losing permission after presign creation prevents completion.
9. A presigned URL has a short expiration, preferably 5–10 minutes.
10. A pending Document expires at the same time or shortly after the presigned URL.
11. The backend does not accept multipart file bodies.
12. The backend does not stream, buffer, or proxy files.
13. The backend must verify the object with MinIO before marking it available.
14. Client-supplied size, MIME type, checksum, and ETag are not authoritative.
15. The complete action is idempotent.
16. An available Document cannot be completed again with different object metadata.
17. Expired pending Documents cannot be completed.
18. Failed verification must never make the Document downloadable.
19. Downloads remain permission-scoped and use short-lived presigned GET URLs.
20. Presigned URLs must never appear in logs, audit metadata, exceptions, or outbox payloads.

## API 1: Create presigned upload

```text
POST /api/v1/documents/presign/
```

Authentication:

```text
Authorization: Bearer <access-token>
```

Required header:

```text

```

### Request

```json
{
  "matter_id": "matter-uuid",
  "filename": "contract.pdf",
  "content_type": "application/pdf",
  "size": 245789,
  "checksum_sha256": "optional-lowercase-hex-value",
  "description": "Signed contract"
}
```

The API must not accept:

```text
organization_id
object_key
bucket
status
uploaded_by
uploaded_at
minio_credentials
access_key
secret_key
```

### Recommended response using presigned POST

```json
{
  "document": {
    "id": "document-uuid",
    "filename": "contract.pdf",
    "status": "pending_upload",
    "upload_expires_at": "2026-07-15T18:10:00Z"
  },
  "upload": {
    "method": "POST",
    "url": "https://minio.example.test/legal-documents",
    "fields": {
      "key": "organizations/.../documents/...",
      "policy": "...",
      "x-amz-signature": "..."
    },
    "expires_at": "2026-07-15T18:10:00Z"
  }
}
```

Presigned POST is preferred because policy conditions can restrict:

* exact object key;
* permitted content type;
* maximum file size;
* expiration.

If the current MinIO client supports only presigned PUT cleanly, the response may instead be:

```json
{
  "document": {
    "id": "document-uuid",
    "filename": "contract.pdf",
    "status": "pending_upload",
    "upload_expires_at": "2026-07-15T18:10:00Z"
  },
  "upload": {
    "method": "PUT",
    "url": "https://minio.example.test/...",
    "headers": {
      "Content-Type": "application/pdf"
    },
    "expires_at": "2026-07-15T18:10:00Z"
  }
}
```

Do not return both approaches.

Use one explicit implementation.

## Presign validation

Before creating the Document:

1. Authenticate the User.
2. Load the matter through a permission-scoped selector.
3. Confirm the User may upload documents.
4. Validate filename length and extension.
5. Validate allowed MIME type.
6. Validate maximum file size.
7. Validate checksum syntax when provided.
8. Check organization upload quotas when implemented.
9. Apply the dedicated upload-presign rate limit.
10. Generate the Document UUID.
11. Generate the object key.
12. Create the pending Document.
13. Create the presigned URL.
14. Return only safe metadata.

If presign generation fails, do not leave a usable pending Document without recording a failed state or rolling back the transaction.

## Completion verification

Inside the completion service:

1. Authenticate the User.
2. Load the Document through an organization- and permission-scoped selector.
3. Re-check current upload permission for the related matter.
4. Lock the Document row with `select_for_update()`.
5. Confirm the status is `pending_upload` or safely replayable.
6. Confirm the upload has not expired.
7. Set status to `verifying`.
8. Perform MinIO `stat_object` or equivalent HEAD operation.
9. Verify:

   * bucket is the expected private bucket;
   * object key equals the backend-stored object key;
   * object exists;
   * object size equals expected size;
   * content type is permitted;
   * metadata matches required policy;
   * checksum matches when supported and configured.
10. Reject zero-byte objects unless explicitly permitted.
11. Reject objects larger than the configured limit.
12. Store safe verified metadata.
13. Set status to `available`.
14. Set `uploaded_at`.
15. Write the activity record.
16. Create the transactional outbox event.
17. Commit atomically.

Do not trust a client-submitted object key.

Do not accept the object key in the complete request.

## Verification failure

When verification fails:

1. Set status to `failed`.
2. Record a safe machine-readable failure code.
3. Attempt to remove the invalid object from MinIO through a background task or safe cleanup operation.
4. Do not expose raw MinIO errors to the User.
5. Do not mark the Document available.
6. Publish a safe failure event.

Stable failure codes may include:

```text
upload_object_missing
upload_expired
upload_size_mismatch
upload_content_type_mismatch
upload_checksum_mismatch
upload_verification_failed
```

## Idempotency

The presign endpoint must support `Idempotency-Key`.

Same key and same request:

```text
Return the original pending Document and valid response when safely replayable.
```

Same key and different request:

```text
409 idempotency_conflict
```

The complete action must also be idempotent:

* completing an already available Document returns the current safe representation;
* no duplicate activity is written;
* no duplicate outbox event is created;
* a failed or expired Document is not silently changed to available.
