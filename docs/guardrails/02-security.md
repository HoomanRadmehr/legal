# Security guardrail

## Threats in scope

- Cross-organization data exposure.
- Insecure direct object reference to confidential matters or documents.
- Role escalation.
- Stolen or replayed refresh tokens.
- CSRF on cookie-authenticated endpoints.
- Brute-force login and resource exhaustion.
- Upload of oversized, unexpected, or mismatched objects.
- Leaked presigned URLs or credentials.
- WebSocket ticket reuse or cross-user event subscription.
- Missing audit evidence.
- Sensitive data in logs.

## Authentication

- Use a maintained JWT package; do not implement cryptography.
- Access tokens are short-lived and sent in `Authorization: Bearer`.
- Refresh tokens are rotated and stored in an HttpOnly cookie.
- Provide a safe CSRF bootstrap endpoint. Login, refresh, and logout require CSRF because they set or use authentication cookies.
- Production cookies are Secure and have an explicit SameSite policy.
- Logout blacklists or revokes the current refresh token.
- Password change and account deactivation invalidate existing refresh capability.
- Authentication errors do not reveal whether an email or username exists.

## Authorization and tenancy

- Every organization-owned selector begins with organization scope.
- Matter visibility is applied before retrieving by ID.
- Domain service functions re-check mutation permissions; they do not rely solely on the ViewSet permission class.
- A request cannot choose another organization through payload data.
- Cross-organization assignees, owners, access grants, and relations are rejected.
- Confidential object lookups normally return `404` when not visible.

## CSRF, CORS, and browser security

- CORS uses explicit origins; never use wildcard with credentials.
- CSRF trusted origins are environment-specific.
- Login, refresh, logout, and other cookie-changing/authenticated endpoints use CSRF; bearer-token domain APIs still validate origin/CORS at the browser boundary.
- Production enables HSTS, HTTPS redirect, secure cookies, content-type sniffing protection, and frame denial.
- The reverse proxy sets appropriate request size and timeout limits.

## Rate limiting

Apply two layers:

1. Reverse proxy: IP burst rate, connection rate, body size, slow-client limits, WebSocket connection limits.
2. DRF Redis-backed throttles: anonymous, authenticated burst, sustained, login, refresh, upload initiation, upload completion, WebSocket ticket, export, and offboarding.

Return `429` with `Retry-After` and the standard error envelope.
Do not describe DRF throttling as the sole defense against a distributed attack.

## Document storage

- Private bucket only.
- Random object key generated by the backend.
- Short upload and download TTLs.
- Permission check before every URL issuance.
- Upload session controls expected size, MIME type, extension, checksum when available, and expiration.
- Completion verifies the object using MinIO metadata; client claims are not trusted.
- Download is allowed only for `available` documents.
- Never log a presigned URL.
- Document processing failures do not expose internal storage errors to the client.

## WebSocket

- Issue a one-time ticket over authenticated HTTP.
- Store ticket state in Redis with a 30-60 second expiry.
- Delete the ticket on first successful use.
- Validate allowed origins.
- Connect users only to server-selected user groups.
- Do not allow the client to subscribe to arbitrary organization, user, or upload group names.
- Configure application and reverse-proxy logs to omit or redact the WebSocket ticket query value.
- Enforce message-size and connection limits.
- WebSocket events contain no secret URL or token.

## Audit and logging

Never log:

- passwords;
- access or refresh tokens;
- cookie values;
- presigned URLs;
- provider secrets;
- document bodies;
- full sensitive payloads.

Structured operational logs may include request ID, actor ID, organization ID, route template, status, duration, and safe event code.
Activity logs record critical business actions but redact secret and unnecessarily sensitive field values.

## Required security tests

- Organization A cannot list, retrieve, update, download, or subscribe to Organization B data.
- Viewer cannot mutate.
- Counsel cannot reassign ownership or offboard.
- Expired/reused refresh and WebSocket tickets fail.
- Login and upload limits return `429`.
- Upload completion rejects wrong object, size, key, expired session, and duplicate misuse.
- Presigned download is denied without matter access.
- Stale version writes return `409`.
- Offboarding is rolled back on failure.
